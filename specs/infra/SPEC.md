# Инфраструктура — Terraform

## Регионы

Один регион: **`us-east-1`**. Там же ACM-сертификаты и WAF со `scope = CLOUDFRONT` — оба обязаны быть именно в нём.

Регион выбран по доступности моделей Bedrock: там они появляются раньше и шире всего, а выбор модели ограничивает продукт.

Мультирегион рассматривался и отклонён: выигрыш — сотни миллисекунд до первого токена для далёких пользователей, цена — API Gateway вместо Function URL, сертификаты в каждом регионе, Global Table с неатомарной квотой и агрегация метрик. Для MVP размен не окупается.

## Состояние

S3-бэкенд с версионированием и блокировкой. Бакет состояния создаётся отдельно и в общий Terraform не входит.

**Окружение одно — prod.** Отдельного dev нет: он удваивает инфраструктуру, домены и сертификаты ради стенда, на котором некому работать.

Отладка идёт против прода. Расширение загружается распакованным, но с фиксированным `key` в манифесте — тогда идентификатор совпадает с релизным и правило `Origin` на WAF срабатывает без исключений. Свободные лимиты для себя выдаются через переопределение по `deviceId`, механизм для этого уже есть.

## Структура

```
infra/terraform/
  main.tf, variables.tf, outputs.tf    единственный корень
  modules/
    api/           lambda, function url, iam, log group
    cdn/           cloudfront, acm, waf, route53 для api
    data/          dynamodb

    budget/        budget, алармы
    artifacts/     s3 для собранных архивов
```

## Модуль `api`

- `aws_lambda_function` — Go на `provided.al2023`, `arm64`, 128 МБ, таймаут 50 с, зарезервированная конкурентность, без VPC. Код берётся из S3: `s3_bucket`, `s3_key = var.lambda_version`, см. «Выкат».

**Зарезервированная конкурентность — 5.** Считается не по Lambda, а по Bedrock: один запрос клиента — до шести обращений к модели, пять из них одновременных. Пять функций дают до тридцати параллельных вызовов Bedrock, и упрёмся мы в квоты модели заметно раньше, чем в лимиты Lambda. Цифра — потолок расхода на старте, а не расчёт под нагрузку; поднимается по мере того, как станет ясен реальный профиль.
- `aws_lambda_function_url` — `authorization_type = "AWS_IAM"`, `invoke_mode = "RESPONSE_STREAM"`.
- `aws_lambda_permission` — вызов разрешён только принципалу `cloudfront.amazonaws.com` с условием на ARN дистрибуции.
- `aws_cloudwatch_log_group` — retention по переменной.

IAM-политика роли, минимальная:

| Действие | Ресурс |
|---|---|
| `bedrock:InvokeModelWithResponseStream` | конкретные ARN моделей и inference profile |
| `dynamodb:UpdateItem`, `dynamodb:GetItem` | ARN одной таблицы |
| `cloudwatch:PutMetricData` | своё пространство метрик |
| `logs:*` | своя log group |

Wildcard в ресурсах запрещён.

## Модуль `cdn`

- `aws_cloudfront_distribution` с origin на Function URL.
- `aws_cloudfront_origin_access_control` — `origin_type = "lambda"`, `signing_behavior = "always"`. Без него Function URL доступен напрямую в обход WAF.
- Кэширование **отключено** (`CachingDisabled`): ответы стриминговые и персональные.
- **Таймаут чтения origin — 60 с** (по умолчанию 30). Функция живёт 50 с, и её таймаут обязан наступать первым: иначе на длинном ответе CloudFront обрывает соединение, а пользователь видит транспортную ошибку вместо готового резюме, которое было почти дописано. 60 с — потолок для custom origin без запроса на увеличение квоты; если когда-нибудь понадобится больше, увеличивать придётся оба значения и через поддержку.
- Проброс заголовков: `X-Device-Id`, `X-Catalog-Version`, `Origin`, `Content-Type`, `x-amz-content-sha256`, `CloudFront-Viewer-Country`. Последний CloudFront проставляет сам — благодаря ему функция получает страну и не видит IP. `x-amz-content-sha256` клиент обязан присылать на POST: OAC вписывает его значение в подпись SigV4, без него Function URL отвечает 403.
- `aws_acm_certificate` в `us-east-1` с DNS-валидацией.
- `aws_wafv2_web_acl`, `scope = CLOUDFRONT`:
  - rate-based правило, 60 запросов / 5 минут на IP. Цифра оставлена низкой сознательно: расширение читают дома и в дороге, а не в офисе за общим NAT, где сотня человек делит один адрес. Упрутся — поднимем, ручка в переменной;
  - byte-match на заголовок `Origin`, `STARTS_WITH` — пропускать всё, что начинается на `chrome-extension://`, остальное 403. Исключений по путям нет и не должно появиться: все эндпоинты API — POST, а на POST браузер проставляет `Origin` всегда. Первый же GET-путь в API потребовал бы исключения и сделал бы это правило дырявым;

    **Конкретный id не проверяется, и переменной `extension_id` больше нет.** Правило покупает исключение веб-страниц: `Origin` браузер проставляет сам по источнику страницы, подменить его скриптом нельзя, и встроить API в сайт поэтому невозможно. Имя одного id сверх этого давало меньше, чем казалось. Распакованная сборка выводит id из абсолютного пути к своей папке, то есть каждая машина разработки — другое расширение; а скриптовый клиент шлёт любой `Origin`, какой захочет, и магазинный id всё равно публичен. Проверка id разворачивала своих и пропускала настойчивых. Правильная фиксация личности — `EXTENSION_KEY` в манифесте: он даёт всем сборкам один стабильный id, и когда он появится, правило можно вернуть к списку идентификаторов;
  - `AWSManagedRulesCommonRuleSet`.
- **Обработки `OPTIONS` нет.** Расширение ходит на хост из `host_permissions`, а такие запросы идут в обход CORS — preflight не случается вовсе, отвечать не на что. Заодно снята нереализуемая часть: CloudFront сам на `OPTIONS` не отвечает, для этого понадобилась бы отдельная CloudFront Function, то есть код и деньги ради ситуации, которой нет.
- `aws_route53_record` — ALIAS `api` → дистрибуция.

Проверка `Origin` живёт здесь, а не в Lambda: отклонённый запрос не порождает вызова функции. Вместе с OAC это значит, что до кода вообще не доходит ничего постороннего.

## Модуль `data`

`aws_dynamodb_table`:

| Параметр | Значение |
|---|---|
| `billing_mode` | `PAY_PER_REQUEST` |
| Hash key | `pk` (string) |
| TTL | атрибут `ttl`, включён |
| PITR | **включён** |

Одна таблица на два вида записей: счётчики квот с TTL и переопределения по устройству без TTL.

PITR включён именно из-за вторых: счётчики эфемерны и восстановлению не подлежат по смыслу, а переопределения заводятся руками и при случайном удалении восстановить их будет неоткуда.

## Модуль `landing`

Приватный S3 + CloudFront с OAC, сертификат в `us-east-1`, ALIAS на apex. Публичный доступ к бакету заблокирован.

### Кэширование включено

В отличие от API, здесь всё статическое и одинаковое для всех.

| Что | TTL | Почему |
|---|---|---|
| Ассеты с хэшем в имени | год, `immutable` | имя меняется при изменении содержимого |
| HTML | 5 минут | правка `/welcome` должна доехать до пользователей без инвалидации |
| Всё остальное | час | |

Политика — `Managed-CachingOptimized`. Строка запроса **в ключ кэша не входит**: `/rate-us?stars=3` и `/rate-us?stars=5` — одна и та же страница, значение читает JavaScript на стороне клиента. Иначе получим пять копий одного файла в кэше.

Инвалидация `/*` выполняется при выкате. При пятиминутном TTL на HTML она нужна редко, но для срочной правки должна быть в скрипте деплоя, а не набираться руками в консоли.

### Маршруты

| Путь | Назначение | Состояние |
|---|---|---|
| `/` | лендинг | отдельно |
| `/welcome` | открывается после установки расширения | заглушка |
| `/uninstall` | открывается после удаления | редирект на форму обратной связи |
| `/rate-us` | развилка по оценке | форма подключена, адрес магазина — заглушка |

Все три служебные страницы лежат в бакете как `<путь>/index.html`.

**CloudFront сам не подставляет index в подкаталогах.** Нужна CloudFront Function на viewer request, дописывающая `/index.html` к путям без расширения. Без неё `/welcome` вернёт 403, и это выяснится ровно в момент, когда первый пользователь установит расширение.

`/welcome` — заглушка, содержимое делается отдельно.

`/uninstall` — безусловный редирект на форму обратной связи. Адрес задан дважды: в `<meta http-equiv="refresh">` и в `location.replace()`. Первое работает без JavaScript, второе быстрее; что сработает первым, то и уводит, второму делать уже нечего. `replace`, а не `assign`: человек попал сюда, удалив расширение, и «Назад» должно вернуть его туда, где он был до этого, а не на эту же страницу.

**Страница остаётся страницей, а не 302 на CloudFront.** Редирект на уровне дистрибуции был бы быстрее, но обращение к `/uninstall` попало бы в логи со статусом 302, а весь счёт удалений построен на `sc-status = 200`. Держать разметку ради одного заголовка — небольшая цена за то, чтобы способ считать не зависел от способа уводить.

`/rate-us` содержит рабочую логику: читает `?stars=`, при 4–5 отправляет в Chrome Web Store, при 1–3 — в форму обратной связи. Адрес формы подставлен; адрес магазина остаётся плейсхолдером, пока расширения нет в магазине, и до тех пор оценка 4–5 ведёт в никуда.

**Оценка в форму не передаётся.** Ссылка `forms.gle` отбрасывает любую строку запроса: она отвечает 302 на канонический адрес формы, где остаётся только `usp=send_form`. Параметр `entry.<id>=` здесь был бы предзаполнением, которое молча не срабатывает. Чтобы число доехало, нужен развёрнутый адрес `/forms/d/e/<id>/viewform` и id поля.

Все три закрыты от индексации.

## Логи

Два переключателя, `waf_logs_enabled` и `cloudfront_logs_enabled`, оба по умолчанию включены. Они отвечают на разные вопросы и стоят по-разному.

| Переключатель | Что пишется | Объём |
|---|---|---|
| `waf_logs_enabled` | что остановлено и каким правилом, с заголовками запроса | доли процента трафика — фильтр отбрасывает разрешённое |
| `cloudfront_logs_enabled` | всё, что доехало до дистрибуции, включая разрешённое | весь трафик |

Первый предназначен оставаться включённым: он дёшев и отвечает на вопрос «почему у пользователя 403». Второй фильтра не имеет и растёт с трафиком, а не с числом инцидентов — его выключают обратно, когда вопрос, ради которого включали, закрыт.

**Выключенный `waf_logs_enabled` обнуляет выходное значение `waf_log_group_name`, а не оставляет его валидным.** Это сделано ради отчёта: по пустому имени он говорит «секция недоступна», а имя, продолжающее работать при выключенной доставке, превратило бы «никто не считал» в «никого не заблокировали» — ложь в самую успокаивающую сторону.

## Логи WAF

WebACL пишет заблокированные и посчитанные запросы в лог-группу `aws-waf-logs-mis-api`. Имя не вкусовое: WAF отказывает любому назначению в CloudWatch, чья группа не начинается на `aws-waf-logs-`, а сообщение об ошибке про префикс не говорит ничего.

**Пишутся только заблокированные запросы.** `logging_filter` оставляет `BLOCK`, остальное отбрасывается до записи. Следствие, которое надо держать в голове при чтении отчёта: пустая секция WAF означает «никого не остановили», а не «никто не приходил».

Изначально удерживался ещё и `COUNT` — из соображения, что посчитанное правило тоже сработало, а вместе это доли процента трафика. Оценка оказалась неверной, и логи это показали: `SizeRestrictions_BODY` намеренно переведён в `count`, тело реального запроса регулярно больше его лимита в 8 КБ, и почти каждый настоящий запрос удерживался как посчитанный. Фильтр делал ровно то, что записано; ошибочной была оценка частоты.

Сами счётчики при этом не потеряны: управляемая группа публикует их метриками CloudWatch, и вопрос «срабатывает ли правило размера» решается там. Потеряна пообъектная детализация за ними; вернуть её — добавить условие `COUNT` обратно на то время, пока вопрос открыт.

**`X-Device-Id` вырезается через `redacted_fields`.** WAF пишет заголовки запроса целиком, и идентификатор устройства среди них. В разрешённый список логируемого он не входит, и в группе, которая существует ради счёта срабатываний правил, ему делать нечего.

Метрики WebACL при этом остаются: они отвечают «сколько», логи — «чем именно» и «как часто каждым правилом».

## Логи CloudFront

Standard logging v2 в CloudWatch Logs, группа `/aws/cloudfront/mis-api`. Три ресурса доставки: `aws_cloudwatch_log_delivery_source`, `..._destination`, `aws_cloudwatch_log_delivery`.

Не блок `logging_config` у самой дистрибуции: тот пишет в S3 и требует бакета с включёнными ACL, которые на любом бакете последних лет выключены по умолчанию. Включать их обратно ради лога, который из S3 всё равно никто не читает, — не тот размен.

Записи появляются с задержкой в несколько минут после запроса; это свойство доставки, а не признак поломки.

## Модуль `bot`

Telegram-бот, отдающий тот же отчёт по команде. Вебхук на Lambda Function URL, не long polling: long polling требует процесса, который работает всегда, а этот живёт несколько секунд в сутки.

Бинарник — тот же, что у CLI `apps/reporter`, собранный под Lambda. Это сделано намеренно: отчёт в чате и отчёт в терминале оказываются одним кодом и не могут разойтись в показаниях об одном и том же часе.

### Чем закрыт открытый эндпоинт

Telegram ничего не подписывает и умеет только «вот URL», поэтому `authorization_type = NONE` — иначе никак. Защита сдвинута внутрь функции и состоит из трёх слоёв, проверяемых в этом порядке:

1. **Секретный токен.** Telegram шлёт значение, заданное при `setWebhook`, в заголовке `X-Telegram-Bot-Api-Secret-Token` на каждом вызове. Сравнение постоянного времени. Это дверь: без него запрос не проходит первую проверку.
2. **Белый список чатов.** Боты находятся по имени пользователя, то есть написать боту может кто угодно, и Telegram донесёт это сообщение с правильным секретом. Список чатов — единственное, что делает такие сообщения бесполезными.
3. **Резервированная конкурентность.** Ограничивает радиус поражения. Сейчас `null`: аккаунтный потолок Lambda равен 10, а AWS отклоняет любое резервирование, оставляющее меньше 10 нерезервированных. Ставится в 2, когда потолок поднимут.

Неугадываемость самого URL защитой не считается: он лежит в настройках Telegram и попадает в любой лог, который его увидит.

**Окна ограничены пятью.** CLI принимает любую длительность, бот — только `30m`, `1h`, `12h`, `24h`, `month`. Запрос Insights оплачивается по просканированным байтам, и неограниченное окно, приезжающее сообщением в чат, — это неограниченный счёт, приезжающий сообщением в чат.

### Секрет

`aws_secretsmanager_secret` с именем `mis-bot`, JSON вида `{"botToken": "...", "webhookSecret": "..."}`. Terraform создаёт коробку и никогда не узнаёт, что в неё положили: токен в `tfvars` был бы закоммичен, токен в переменной лежал бы в state открытым текстом. Версия-плейсхолдер создаётся с `ignore_changes = [secret_string]` — иначе следующий `apply` затёр бы настоящий токен обратно в пустой.

Функция читает секрет один раз на холодном старте и падает с `log.Fatal`, если его нет или он неполон. Это осознанно: бот без токена не может ничего, и сказать об этом один раз громко лучше, чем по разу на каждое сообщение.

**Пока белый список пуст**, бот отвечает единственное — идентификатор чата, из которого пришло сообщение. Иначе первое значение для списка неоткуда взять. Как только в списке появляется хоть один чат, всем остальным бот не отвечает вовсе.

## Логи лендинга

Дистрибуция лендинга пишет свои access-логи в `/aws/cloudfront/mis-landing`, тем же механизмом standard logging v2. Переключатель — `landing_logs_enabled`.

Нужны они ради одной страницы. `/uninstall` — то, куда Chrome отправляет пользователя, удалившего расширение, и обращение к ней единственный след этого события. Спросить больше некого: расширения к этому моменту уже нет и отчитаться оно не может, а форма по редиректу считает отправивших, а не пришедших.

**Список полей выписан явно, а не оставлен по умолчанию.** Умолчание — классический набор из 33 колонок, и поля со страной в нём нет. Оставлены семь: `timestamp`, `c-country`, `cs-uri-stem`, `sc-status`, `cs(User-Agent)`, `cs(Referer)`, `x-edge-result-type`. Каждая лишняя колонка — это байты на каждый запрос навсегда, а лог отвечает на три вопроса: сколько, откуда, когда.

Считать обращения к `/uninstall` за удаления можно только приблизительно: страница публична, и запрос к ней может сделать кто угодно — краулер, префетч, повторное открытие вкладки. `cs(User-Agent)` и `x-edge-result-type` оставлены именно для того, чтобы очевидный мусор было чем отсечь.

## Модуль `budget`

- `aws_cloudwatch_metric_alarm` на суточную сумму метрики `EstimatedCostUsd` — порог `daily_cost_alarm_usd`. Основной механизм: функция считает расход сама по токенам, задержка минуты.
- `aws_budgets_budget` с оповещением на 50%, 80%, 100% — страховка на весь аккаунт. Данные биллинга отстают на часы, поэтому это не механизм остановки.
- Остальные алармы из спеки бэкенда, SNS на email.

### Аларм «ноль успешных ответов»

Одной метрикой он не выражается: «ноль успехов» при нулевом трафике — это ночь, а не авария, и алярм, орущий каждую ночь, выключают через неделю.

Поэтому `aws_cloudwatch_metric_alarm` с `metric_query` (metric math), два входа за окно 3 часа:

```
m1 = Invocations           (сумма)
m2 = Successes             (сумма, своя метрика функции)
alarm: m1 >= min_invocations_for_alarm AND m2 == 0
```

Условие по `m1` и есть та самая «при обычном трафике»: без него алярм неотличим от датчика ночного простоя. `min_invocations_for_alarm` — переменная, потому что правильное значение зависит от реального суточного профиля, которого пока нет.

`Successes` функция публикует сама: успехом считается ответ, дошедший до `done`. Штатная метрика Lambda для этого не годится — ошибка, отданная как SSE-событие `error`, с точки зрения Lambda успешный вызов.

Разворачивается вместе с остальным, не «потом».

### Наборы тиров собираются полными

Оба набора разрешаются в `locals` **до** передачи в лямбду: незаданное поле подменяется базой здесь, а не в функции. В окружение уезжают полные `TIER1_*` и `REST_*`, а `DEFAULT_*` там нет вовсе.

Причина в том, что окружение лямбды — это то, куда смотрят при разборе инцидента, и оно обязано отвечать на вопрос «чем отвечали запросы из этой страны» само, без чтения кода функции. Пустое значение со смыслом «возьми уровнем ниже» этому прямо мешает: видно, что не задано, и не видно, что действует. Отсюда правило на все переменные окружения функции — **дефолт выписан явно**, включая `CATALOG_PATH`, который функция и так умеет подставить сама.

Цена размена — одно и то же число уезжает в две переменные окружения, и база остаётся ручкой «поменять сразу для всех», но живёт только в Terraform. Прямое следствие для функции: цепочка разрешения стала двухуровневой, переопределение устройства поверх полного набора тира, и третьего уровня в ней больше нет.

`max_actions` в тиры не сворачивается и остаётся отдельной глобальной переменной: это число уезжает в промпт до первой точки кэширования, и разное по тирам раздробило бы prompt-кэш. Значения в тирах его превышать не могут — функция проверяет это при старте и не поднимается.

Всё это уезжает в переменные окружения Lambda и **не покидает сервер**: эндпоинта, раздающего конфиг расширению, в API нет. Клиент видит только последствия — код ошибки в ответе на свой запрос.

`enabled = false` — аварийный выключатель: функция отвечает `service_disabled` первым шагом конвейера, до квоты и до Bedrock. `disabled_message` — необязательный текст на английском (причина, ожидаемый срок), который расширение покажет как есть; пусто — покажет свою локализованную строку.

Смысл: срезать лимиты, сменить модель или выключить сервис можно через `terraform apply`, не дожидаясь ревью в Chrome Web Store. Действует со следующего запроса каждого клиента — кэшировать эти значения на устройстве нечему.

Когда число переменных станет неудобным, набор переезжает в один JSON в SSM Parameter Store — тогда правка перестанет требовать даже `terraform apply`. Для MVP переменных достаточно.

## Модуль `artifacts`

`aws_s3_bucket` `mis-artifacts`: приватный, публичный доступ заблокирован, версионирование включено, шифрование по умолчанию.

Раскладка:

```
lambda/<short-sha>.zip        бинарник функции, его читает Terraform
extension/<manifest-version>.zip   то, что ушло в Chrome Web Store
```

Архив расширения Terraform не нужен и хранится по другой причине: магазин не отдаёт обратно то, что вы в него загрузили, а знать, какая именно сборка сейчас у пользователей, необходимо при разборе жалоб.

Жизненный цикл не настраивается: архивы весят мегабайты, а история выкатов — это история отката.

## Выкат

Никакого пайплайн-сервиса на MVP нет. Есть `make-release.sh` и `terraform apply`, и разделены они по границе «собрать» / «выкатить».

**Скрипт собирает и кладёт, Terraform выкатывает.**

```
make-release.sh
  1. go build → GOOS=linux GOARCH=arm64, zip
  2. aws s3 cp → s3://mis-artifacts/lambda/<short-sha>.zip
  3. сборка расширения → zip
  4. aws s3 cp → s3://mis-artifacts/extension/<manifest-version>.zip
  5. печатает <short-sha> — значение для lambda_version
```

Выкат — правка `lambda_version` и `terraform apply`. **Откат — та же правка на прежнее значение и тот же `terraform apply`.** Артефакты никуда не деваются, откат не требует ни сборки, ни доступа к машине разработчика, ни git.

Скрипт **ничего не выкатывает сам** и прав на `lambda:UpdateFunctionCode` не имеет. Это осознанно: иначе появляются два способа изменить прод — через Terraform и мимо него, — и состояние, которое видит Terraform, перестаёт соответствовать действительности. Тогда следующий `apply` откатит функцию на то, что записано в переменной, в неожиданный момент и без предупреждения.

**Ключ содержит git-хэш, а не порядковый номер.** Номер надо где-то вести, а хэш уже есть и однозначно указывает на исходный код. Заодно ключ меняется при каждой сборке, и Terraform видит изменение без `source_code_hash`.

Расширение в магазин загружается вручную: у Chrome Web Store своё ревью в несколько дней, автоматизировать вокруг этого нечего.

**Курица и яйцо при первом применении:** модуль `api` требует существующего объекта в S3. Поэтому `artifacts` применяется первым, затем прогоняется `make-release.sh`, и только потом `api`. Отражено в порядке ниже.

## Именование и теги

Ресурсы: `mis-<компонент>`.

Обязательные теги на всех ресурсах: `Project = make-it-shorter`, `ManagedBy = terraform`.

## Что не в Terraform

- Зона Route53 — создана вручную, подключается через `data`-источник. Записи внутри зоны — в Terraform.
- Бакет состояния.
- **Сборка** кода Lambda — делает `make-release.sh`. Сам выкат при этом **в Terraform**: функция ссылается на объект в S3, а какой именно — решает переменная `lambda_version`. Мимо Terraform прод не меняется.
- Загрузка расширения в Chrome Web Store.
- Доступ к моделям Bedrock — включается в консоли аккаунта один раз.

## Временное: ручные ресурсы на время разработки бэкенда

Пока пишется и отлаживается функция, нужные для этого ресурсы **заводятся руками**, через консоль или AWS CLI, минуя Terraform. Разработке нужен быстрый цикл, а не `apply` на каждый чих.

Разрешено заводить руками: включение доступа к моделям Bedrock, роль и политику для локальных вызовов, временные лог-группы, пробные вызовы модели.

**Это долг, и он гасится до выката.** К моменту, когда бэкенд готов, всё перечисленное обязано быть описано в Terraform, а ручные ресурсы — удалены или взяты под управление через `import`. Проверка простая: развернуть с нуля в пустом аккаунте одним `terraform apply` и убедиться, что функция работает.

Опасность именно в том, что ручной ресурс работает. Он не напоминает о себе никогда — пока не понадобится восстановить окружение или объяснить, откуда взялась политика, которой нет в коде.

## Порядок первого применения

1. Проверить, что выбранная модель есть в `us-east-1` и поддерживает там strict tool use. От этого зависит выбор модели.
   **Наличие подтверждено** (`bedrock list-foundation-models`, аккаунт 501631673704): `anthropic.claude-haiku-4-5-20251001-v1:0` и `amazon.nova-lite-v1:0` — обе `ACTIVE`. Strict tool use и стриминг проверяются только реальным вызовом, это остаётся.
2. `data`, `budget`, `artifacts`.
3. Прогнать `make-release.sh` — без объекта в S3 модуль `api` не применится.
4. `api` с функцией-заглушкой, отдающей поток.
5. `cdn`, дождаться валидации сертификата.
6. **Проверить, что SSE доезжает до браузера по частям, а не одним куском.** Главный технический риск проекта; снимается до продуктовой логики.
7. `landing` с CloudFront Function для подкаталогов.
