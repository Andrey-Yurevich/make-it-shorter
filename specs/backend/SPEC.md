# Бэкенд

Одна Lambda на Go в одном регионе (`us-east-1`), Function URL в режиме `RESPONSE_STREAM`. Роутинг по пути внутри функции.

**Код наивный и читаемый, весь на английском** — общее правило и его обоснование в CLAUDE.md. Здесь оно действует в полную силу: вся функция обязана читаться сверху вниз за один проход.

Практически это значит, что конвейер из спеки ниже должен узнаваться в коде **буквально**: последовательность шагов 0–7 читается как последовательность вызовов в одной функции, а не собирается из цепочки middleware, обработчиков и интерфейсов. Тот, кто через полгода будет чинить прод в три часа ночи, должен находить нужный шаг поиском по имени, а не трассировкой.

## Эндпоинты

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/v1/summarize` | сжать текст, предложить кнопки и сразу ответить на каждую |

**Эндпоинт ровно один, и он POST.** Роутинг по пути внутри функции остаётся — он ничего не стоит и даёт куда добавить второй путь, когда он понадобится.

Health-эндпоинта нет. Балансировщика, который выводил бы нездоровые инстансы из ротации, в схеме не существует, а живость видна по метрикам реальных вызовов.

Эндпоинта, раздающего клиенту лимиты и флаг доступности, нет тоже. Лимиты применяет сервер и сообщает о них кодом ошибки; аварийный выключатель — код `service_disabled` на первом же запросе. Клиенту достаточно кода: копия серверных значений у него на руках ничего не решает, а стоила бы кэша с окном протухания и второго пути в API со своим профилем доступа.

Отдельный GET-путь потребовал бы ещё и исключения в правиле `Origin` на WAF: на GET из расширения браузер этот заголовок не гарантирует. Исключение открыло бы дырку, а без исключения путь молча резался бы — то есть выключатель отказывал бы ровно тогда, когда нужен.

Эндпоинта за уточнением нет намеренно. Уточнения ко всем предложенным кнопкам генерируются здесь же и уезжают тем же потоком; нажатие на кнопку в сеть не ходит. Обоснование размена — в CLAUDE.md, «Уточнения генерируются заранее, все сразу».

### `/v1/summarize`

```
text   string
lang   string
tone   original | diplomatic | formal | professional | confident | friendly | academic
       | casual | simplified | bold | empathetic | direct | luxury | persuasive | engaging
source selection | page | manual
```

Stateless: текст живёт в памяти функции, пока идёт ответ. Серверное хранение или кэширование пользовательских текстов запрещено.

Ответ — SSE по протоколу из спеки архитектуры: `delta`* → `actions` → `answer`* → `done`.

## Конвейер обработки

0. Флаг доступности сервиса → `service_disabled`.
1. Валидация тела и заголовков → `invalid_request`; `lang` по списку из переменных окружения → `unsupported_language`.
2. Проверка длины по порогам из переменных окружения → `too_short` / `too_long`. Считается в **Unicode code points** (`utf8.RuneCountInString`), не в байтах: на кириллице и CJK байты дают двух-трёхкратное превышение и валят текст, который клиент честно пропустил. Эвристик «осмысленный ли текст» нет.
3. Квота в DynamoDB → `rate_limited`.
4. **Фаза 1.** Bedrock `ConverseStream`: резюме + вызов `suggest_actions`.
5. Текстовые чанки → `delta`; после закрытия потока фильтрация ID → `actions`.
6. **Фаза 2.** По одному вызову Bedrock `Converse` на каждый оставшийся ID, **параллельно**. Каждый завершившийся → `answer`.
7. `done`.

Шаги 0–3 выполняются **до** обращения к Bedrock. Ошибка на любом — SSE-ответ с единственным событием `error`, код 200 на уровне HTTP.

Шаг 0 — самый первый: выключенный сервис не тратит ни `GetItem`, ни инкремент квоты.

`actions` уходит клиенту **до** начала фазы 2, а не после неё. Кнопки появляются сразу под резюме, пусть и неактивными: иначе пользователь несколько секунд смотрит на готовое резюме без кнопок, а потом они возникают из ниоткуда.

Пустой список ID после фильтрации — фазы 2 нет вовсе, сразу `done`. Флаг и необязательный текст `message` — переменные окружения, меняются через `terraform apply` без релиза расширения. Клиент узнаёт о выключении на первом же запросе, окна протухшего кэша не существует.

Проверки шагов 1–2 дублируют клиентские намеренно. **Сервер здесь единственная инстанция**: клиентская проверка — только экономия запроса, доверять ей нельзя. Обратное тоже верно — сервер не рассчитывает, что клиент отфильтрует хоть что-нибудь.

**`Origin` функция не проверяет.** Это делает WAF на CloudFront: отклонённый запрос не доходит до Lambda, вызов не оплачивается. С учётом OAC запрос с чужим `Origin` до функции физически не доедет.

### Что считается `invalid_request`

Закрытый список:

- тело не парсится как JSON;
- отсутствует или не того типа `text`, `lang`, `tone`, `source`;
- `tone` вне списка из описания эндпоинта;
- `source` вне `selection | page | manual`;
- нет заголовка `X-Device-Id` или `X-Catalog-Version`;
- `X-Device-Id` не UUIDv4;
- `X-Catalog-Version` не целое или меньше 1.

Всё прочее нераспознанное в запросе попадает сюда же — это код по умолчанию для «запрос сформирован неправильно».

Соседние случаи разведены намеренно: `lang` вне списка → `unsupported_language`, длина вне порогов → `too_short` / `too_long`, неизвестный путь → обычный **404 без SSE**.

`invalid_request` означает баг клиента или подделку запроса, а не ошибку пользователя. Пользователю показывается общее «что-то пошло не так»: советовать ему нечего, исправить он ничего не может.

## Bedrock

`ConverseStream`, модель класса Haiku / Nova Lite, обращение через cross-region inference profile.

**`tool_choice: auto`.** Форсировать вызов инструмента запрещено: форсированный выбор подавляет текстовый блок, и резюме не будет.

### Инструмент

```
name: suggest_actions
strict: true
input schema:
  ids:     array, items: enum <полный каталог>
  docType: enum <типы документов, включая other>
  srcLang: string
```

**`maxItems` в схеме нет, и поставить его нельзя.** Constrained decoding его не поддерживает: схема, несущая `strict: true` и `maxItems` одновременно, отвергается с `ValidationException: For 'array' type, property 'maxItems' is not supported`. По отдельности принимается любое из двух.

Выбран `strict`, и выбор не близкий. `maxItems` ограничивал только количество, а `strict` — единственное, что делает ID вне enum физически несоздаваемым; это правило 1 из раздела «Кнопки» в CLAUDE.md, и покупать соблюдение потолка ценой отказа от него нельзя. Отказ при этом не деградация, а полный отказ сервиса: схема отвергается на каждом запросе, то есть падает фаза 1, то есть не будет и резюме.

Потолок вместо этого живёт в двух местах: **просьбой в промпте** («propose at most N ids») и **жёсткой обрезкой** в фильтрации ID после ответа. Первое — мягкое ограничение, которое модель однажды нарушит; второе — настоящая гарантия, и она бесплатна, потому что обрезка идёт до фазы 2 и лишний ID не превращается в вызов модели.

`docType` — тип текста по мнению модели: `news`, `article`, `product`, `scientific`, `legal`, `howto`, `thread`, `other`. Значение `other` обязательно: без запасного варианта закрытый перечень вынуждает модель отнести непонятный текст к ближайшей категории, и статистика начинает врать.

`docType` и `srcLang` идут **только в лог**. Клиенту не передаются, на подбор кнопок и на поведение не влияют. Нужны, чтобы группировать статистику по типу материала при настройке каталога.

`strict: true` даёт constrained decoding: ID вне enum физически не может быть сгенерирован.

Схема инструмента **статична и байт-идентична между запросами**. Динамическая сборка схемы (например, фильтрация enum под версию клиента) запрещена — плодит грамматики и дробит prompt-кэш.

### Порядок запроса

**Две точки кэширования, а не одна.**

```
[системный промпт + каталог + описание инструмента]   ← статика
--- cache breakpoint 1 ---
Output language: <lang>
Tone: <tone>
<текст пользователя>                                   ← общее для обеих фаз
--- cache breakpoint 2 ---
<задача фазы>                                          ← переменная часть
```

Первая точка — как раньше: статика, общая для всех запросов вообще.

Вторая точка — ключевая для новой схемы. Фаза 1 её **записывает**, все параллельные вызовы фазы 2 её **читают**. Без неё исходный текст (до 30 000 символов) уезжал бы в Bedrock шесть раз по полной цене вместо одного раза по полной и пяти по цене чтения кэша. На длинных текстах это и есть основная статья расхода — больше, чем все сгенерированные уточнения вместе.

Порядок обязателен: всё, что общее для фаз, — **до** второй точки, задача фазы — строго после. Нарушение обнуляет кэш и умножает счёт за вход на число кнопок.

Из этого следует неочевидное требование: **блок описания инструмента присутствует в обеих фазах, байт в байт.** Инструмент фазе 2 не нужен, но убрать его — значит изменить префикс и потерять кэш целиком. Он остаётся и просто не используется.

`Tone: <tone>` в фазе 2 тоже остаётся, хотя к уточнению не относится: он внутри кэшируемого префикса, и любая попытка вычистить его оттуда стоит дороже, чем приносит.

**Проверить на раннем этапе:** число точек кэширования, которое допускает выбранная модель в Bedrock, и минимальную длину кэшируемого префикса — короткие тексты могут не дотягивать до порога кэширования, и тогда фаза 2 платит полную цену. Это не ломает схему, но меняет расчёт стоимости на коротком входе.

### Промпт

На английском. Локализация запрещена.

Обязательно содержит **явное указание, когда инструмент вызывать не надо**: текст слишком короткий, бессвязный, не содержит предмета для уточнения. Оставленный неявным, этот случай ведёт себя недетерминированно.

Обязательно содержит и **потолок числа кнопок** — он переехал сюда из схемы инструмента, где `maxItems` несовместим со `strict`. Число берётся из глобального `MAX_ACTIONS` и **никогда** из значения, разрешённого для конкретного устройства: строка лежит до первой точки кэширования, и персональное число раздробило бы префикс по клиентам — ровно та же причина, по которой в схеме запрещён версионный фильтр. Устройству с меньшим потолком служит обрезка при фильтрации ID.

Замер на Haiku 4.5: при девяти доступных кнопках и потолке 5 модель предлагала 3–4, при потолке 2 — ровно 2. Инструкция связывает, но остаётся просьбой, а не гарантией.

Исходный язык текста в промпте не указывается — модель определяет сама.

### Форма и тон

Форма резюме одна и в запросе не выбирается: **один абзац**. Доля («сожми до 20%») здесь не работала бы: модель не считает символы и не умеет попадать в проценты, а на входе от 50 до 30 000 символов одна и та же доля означает несопоставимые вещи. Форма результата задаётся одинаково на любом входе.

**Потолок токенов — предохранитель, а не цель.** `maxSummaryTokens` обрывает генерацию на полуслове, и резюме, упёршееся в него, — это брак, а не «резюме максимальной длины». Поэтому промпт требует укладываться **заведомо ниже** потолка.

`tone` — голос, которым написан абзац. Задаётся в промпте **качественно**, одной строкой на значение:

| Значение | Что просим у модели |
|---|---|
| `original` | сохранить регистр исходника: формальный остаётся формальным, разговорный — разговорным |
| `diplomatic` | тактично и взвешенно, острые углы сглаживаются, сторона не занимается |
| `formal` | строго и сдержанно, полные формы, без сокращений и разговорных слов |
| `professional` | ясно, по-деловому, нейтрально — голос хорошего рабочего письма |
| `confident` | уверенно и определённо, без оговорок там, где их нет в исходнике |
| `friendly` | тепло и доступно, как объясняют тому, кто нравится |
| `academic` | точно и размеренно, аккуратно с утверждениями и их основаниями |
| `casual` | расслабленно и разговорно, сокращения и бытовые слова допустимы |
| `simplified` | простые слова и короткие предложения, без жаргона, понятно новичку |
| `bold` | ярко и хлёстко, сильные глаголы, короткие фразы, без воды |
| `empathetic` | с вниманием к тому, как это переживают люди в тексте |
| `direct` | сразу к делу, без смягчений, вступлений и оговорок |
| `luxury` | утончённо и отполированно, голос премиального бренда |
| `persuasive` | убедительно отстаивать то, что отстаивает текст, и только это |
| `engaging` | живо и интересно, удерживать читателя, ничего не добавляя |

**Тон меняет голос и никогда не меняет содержание**: те же факты, те же утверждения, сказанные иначе. Промпт говорит это явно — иначе `persuasive` и `bold` начинают досочинять, а `simplified` — терять.

Список значений на сервере и в расширении один и тот же, но задан отдельно на каждой стороне, как и список языков. Значение вне списка — `invalid_request`: это баг клиента, а не ошибка пользователя. Тест сборки проверяет, что у каждого значения из списка парсера есть своя строка в промпте: тон, о котором промпт молчит, модель трактовала бы наугад и по-разному от запроса к запросу.

Строка `Tone:` лежит **после** первой точки кэширования, рядом с языком вывода: значение своё у каждого пользователя и статический префикс не дробит.

### Каталог в промпте

Enum схемы даёт модели список допустимых идентификаторов, но не даёт понять, что каждый означает. Поэтому в статическую часть, рядом с описанием инструмента, идёт таблица `id → description` из `catalog.json`:

```
whats_the_catch — предложить, когда в тексте есть условия, оговорки или скрытая цена
...
```

Записи с `deprecated: true` не попадают ни в enum, ни в эту таблицу.

Всё это статика: собирается один раз при старте функции, между запросами байт в байт не меняется и лежит до точки кэширования.

## Фаза 2: уточнения

По одному вызову на каждый ID, оставшийся после фильтрации. Задача фазы — `instruction` этого ID из `catalog.json`, подставленная после второй точки кэширования.

**`Converse`, не `ConverseStream`.** Ответ фазы 2 буферизуется целиком и уходит одним событием `answer`: пользователь в этот момент читает резюме и текста уточнения не видит. Стримить невидимое — значит тащить плумбинг пяти параллельных потоков и их чередование в один SSE ради того, на что никто не смотрит.

**Вызовы параллельны.** Пять последовательных ответов по 250 токенов не укладываются в таймаут; пять параллельных занимают время одного.

**Порядок событий `answer` не определён** — какой вызов первым вернулся, тот первым и уехал. Клиент раскладывает их по `id`, а не по порядку.

**Пока идёт фаза 2, в поток раз в 10 секунд уходит `: ping`.** Это единственный участок ответа, где соединение законно молчит до 25 секунд, а промежуточные прокси такие соединения закрывают. Комментарий SSE стоит десяток байт и клиентом игнорируется по стандарту.

Резюме фазы 1 в промпт фазы 2 **не подставляется**. У модели есть исходный текст — отвечать надо по нему, а не по собственному сжатию, где ответа может не оказаться. Это и есть тот класс отказов, ради закрытия которого схема менялась.

**`tool_choice` в фазе 2.** Предпочтительно `none`, если выбранная модель в Bedrock его принимает. **Проверить на раннем этапе.** Не принимает — оставить `auto` и просто игнорировать блок `toolUse`, если он придёт: схема на это не завязана, лишний вызов инструмента ничего не портит и стоит десяток токенов.

### Отказ отдельного уточнения

Вызов упал или не уложился в срок → события `answer` для этого ID **нет**, и на этом всё: ни повтора, ни кода ошибки, ни падения всего ответа.

Клиент отбрасывает такую кнопку по `done`. Резюме к этому моменту доставлено, и терять его из-за одного уточнения из пяти — худший из возможных разменов.

Отказ **всех** уточнений при непустом списке ID тоже не ошибка: пользователь получает резюме без кнопок. В лог это идёт отдельным полем, потому что устойчивая доля таких случаев означает проблему в фазе 2, а не в подборе кнопок.

## Разбор ответа модели

Речь о фазе 1. Блоки обрабатываются **по типу, а не по порядку** — очерёдность текстового блока и вызова инструмента при `auto` не гарантирована.

| Тип блока | Действие |
|---|---|
| `text` | каждый чанк → событие `delta` |
| `toolUse` | накопить, разобрать; `ids` отфильтровать → событие `actions`; `docType` и `srcLang` → лог |

Инструмент не вызван → `actions` с пустым массивом, фазы 2 нет, сразу `done`. Подстановка дежурных ID запрещена.

Фаза 2 начинается только после **полного** закрытия потока фазы 1: вызов инструмента приходит одним куском в конце, и до него список ID неизвестен.

### Фильтрация ID

Из полученного списка оставить те, что: есть в каталоге; имеют `since <= X-Catalog-Version`. Обрезать до `maxActions`.

Первая проверка — страховка, enum её уже гарантирует. Вторая — обязательная логика совместимости версий, без неё старый клиент получит кнопку без подписи.

Обрезка — **третья и теперь самая дорогая**: каждый переживший её ID превращается в вызов модели. Она же — **единственная настоящая гарантия потолка**: в схеме `maxItems` нет (несовместим со `strict`, см. «Инструмент»), а промпт лишь просит. Здесь режется по значению, разрешённому для этого устройства, и происходит это **до** фазы 2 — модель, предложившая больше положенного, не стоит ни одного лишнего вызова.

## Параметры запроса

Модель, оба потолка токенов, максимум кнопок и дневная квота не константы. Они разрешаются на каждый запрос по цепочке, первое найденное выигрывает:

```
1. переопределение для этого deviceId   (таблица overrides)
2. набор для географического тира        (env)
```

Уровней ровно два, и второй — дно цепочки. **Набор тира задан в переменных окружения целиком**, все пять полей: пустого поля со значением «смотри уровнем ниже» там не бывает, потому что ниже ничего нет. Страна без тира не третий случай — она просто не тир 1 и попадает в `rest`; отсутствующий заголовок страны ведёт себя так же.

Отсюда правило на все переменные окружения функции: **если у значения есть дефолт, он выписан в окружении явно.** Прочитать окружение лямбды достаточно, чтобы знать, чем отвечают запросы обоих тиров, — за значением не надо идти в код.

Глобальный дефолт как таковой не исчез, он переехал на уровень выше и живёт **только в Terraform**: переменные `default_*` — база, на которую накладываются оба набора при сборке окружения. Функция базы не видит и получает уже разрешённые `TIER1_*` и `REST_*`. Ручка «поменять число сразу для всех» осталась одна, а неоднозначности «чем же ответили» в окружении больше нет.

Исключение одно и по необходимости: `MAX_ACTIONS` остаётся глобальным и без формы на тир. Это число уезжает в промпт, а промпт лежит до первой точки кэширования — значение, разное по тирам, раздробило бы prompt-кэш. Тиру с меньшим потолком служит обрезка при фильтрации ID, а `TIER1_MAX_ACTIONS` и `REST_MAX_ACTIONS` не могут превышать `MAX_ACTIONS`: проверяется при старте.

Разрешённый набор пишется в лог — иначе при разборе жалобы непонятно, какой моделью отвечали.

### Тиры

Тир определяется по стране. **IP-адреса собирать не нужно:** CloudFront сам определяет страну на краю и передаёт двухбуквенный код в заголовке `CloudFront-Viewer-Country`. Функция видит `US`, а не адрес.

Два набора: `tier1` и `rest`. Список стран тира 1 и параметры обоих наборов — переменные окружения.

VPN даёт страну выходного узла. Это принимается как есть и не лечится.

### Переопределения по устройству

Отдельная запись в DynamoDB, ключ `device#<deviceId>`, без TTL:

| Поле | |
|---|---|
| `model` | идентификатор модели, необязательно |
| `maxSummaryTokens` | необязательно |
| `maxAnswerTokens` | необязательно |
| `maxActions` | необязательно |
| `dailyQuota` | необязательно |
| `email` | необязательно |
| `note` | зачем заведено, для людей |

Незаполненные поля падают на следующий уровень цепочки.

**Записи создаются вручную.** API самообслуживания нет и не планируется: эндпоинт, позволяющий поднять себе лимиты, — это и есть дыра.

Чтение — один `GetItem` на запрос, рядом с проверкой квоты.

**`email` — персональные данные.** До того как поле начнёт заполняться, нужны политика приватности с упоминанием этого факта, декларация сбора данных в Chrome Web Store и способ удалить запись по запросу. Пустое поле этих обязательств не создаёт.

## Квоты

DynamoDB, одна таблица, два вида записей по префиксу ключа:

| Ключ | Что | TTL |
|---|---|---|
| `quota#<deviceId>#<YYYY-MM-DD>` | счётчик запросов за сутки | +48 часов |
| `device#<deviceId>` | переопределения | нет |

Инкремент — одной операцией `UpdateItem` с `ConditionExpression` на лимит. Чтение с последующей записью запрещено: параллельные запросы обойдут лимит.

### Граница суток

`YYYY-MM-DD` в ключе считается по **центральноевропейскому времени**, зона `Europe/Berlin`.

Зона задаётся именем из базы IANA, а не фиксированным смещением `+01:00`. Смещение сломалось бы дважды в год: летом Германия живёт на UTC+2, и квота у пользователей обнулялась бы в час ночи вместо полуночи. С именованной зоной граница всегда в местную полночь, а сутки перехода длятся 23 или 25 часов — для суточного счётчика безразлично.

**Go в Lambda базу часовых поясов не содержит.** `time.LoadLocation("Europe/Berlin")` на голом `provided.al2023` вернёт ошибку, и если её проглотить — молча получится UTC, то есть тихо не та граница суток. Базу нужно вшить в бинарник импортом `_ "time/tzdata"`, а ошибку загрузки зоны считать фатальной при старте функции, а не в рантайме на живом запросе.

Выбор зоны — вопрос удобства, а не корректности: обнуление должно приходиться на ночь основной аудитории, а не на её вечер. Значение вынесено в переменную окружения и меняется без релиза.

### Судьба сгоревшего запроса

**Инкремент — до вызова Bedrock**, вместе с остальными проверками шага 3. Иначе параллельные запросы проскакивают мимо лимита, пока первый ещё ждёт модель.

Из этого следует, что запрос, упавший с `upstream_error`, **квоту не возвращает**. Пользователь заплатил попыткой за чужой сбой — это несправедливо и принято осознанно.

Возврат означал бы компенсирующую операцию на пути отказа: ещё один `UpdateItem`, который сам может не пройти, и рассуждения о том, что делать, если не прошёл и он. Ради события, которое при работающем сервисе редко, а при неработающем не имеет значения — там пользователю нужен работающий сервис, а не возвращённый счётчик.

Пересмотреть стоит, если доля `upstream_error` окажется заметной: тогда это уже не редкое событие, и чинить надо в первую очередь саму долю.

Единица счёта — **запрос клиента, а не вызов модели.** Один запрос — это до шести обращений к Bedrock, но для квоты он один. Считать вызовы было бы честнее по деньгам и хуже для пользователя: остаток зависел бы от того, сколько кнопок подобрала модель, то есть от решения, которое пользователь не принимал и предсказать не может.

Отказ → `rate_limited`.

Квота 50 в сутки после перехода на предгенерацию стоит примерно вчетверо дороже прежней. Цифра оставлена как есть осознанно — сначала смотрим на реальный расход, режем по факту. Ручка для этого — переменная окружения, релиз расширения не нужен.

Очистка не реализуется — TTL удаляет счётчики сам, переопределения живут до ручного удаления.

Регион один, поэтому `ConditionExpression` даёт настоящую гарантию: обойти лимит параллельными запросами нельзя.

## Логирование

CloudWatch, структурированный JSON, одна запись на запрос.

**Пишем:** длину входа, `source`, `lang`, `tone`, `docType`, `srcLang`, выбранные ID, `emptyActions: boolean`, код страны, разрешённые модель и лимиты, латентность до первого токена, полную латентность, токены, оценку стоимости, код ошибки.

Плюс по фазе 2: число запущенных вызовов, число неудавшихся, `answersFailed: boolean` на случай «не доехало ни одно», латентность самого медленного из параллельных вызовов, доля входных токенов, прочитанных из кэша.

Последнее — не любопытство, а проверка того, что вторая точка кэширования вообще работает. Доля около нуля означает, что схема кэширования сломалась и вход оплачивается шесть раз; по счёту это видно поздно, по этому полю — сразу.

`emptyActions` алярма не имеет, но в логе остаётся: это единственный способ понять, для каких материалов каталог кнопок работает плохо.

**Не пишем ничего из текста пользователя** — ни исходник, ни резюме, ни тексты уточнений, ни фрагменты. Ошибки Bedrock логируются без эхо содержимого запроса.

Устойчиво высокая доля `emptyActions` на нормальном трафике означает, что промпт слишком строг. Смотрится вручную при настройке каталога, алярма не требует.

## Метрики и алармы

| Метрика | Алярм |
|---|---|
| **Расход за сутки** | **> $40** |
| Латентность до первого токена | p95 > 1.5 с |
| Доля `upstream_error` | > 2% за 15 мин |
| Троттлинг Bedrock | любой |
| Ноль успешных ответов | 3 часа подряд при обычном трафике |
| Доля неудавшихся уточнений | > 5% за 15 мин |
| Доля входных токенов из кэша | < 50% за час |

Ноль успешных ответов заменяет собой проверку живости: при живом трафике его отсутствие само по себе сигнал, и стоит это ноль.

Порог расхода поднят с $20: при предгенерации уточнений средний запрос стоит в разы дороже, и прежняя цифра срабатывала бы на обычном трафике.

Доля уточнений и доля кэша — новые и обе про фазу 2. Первая ловит тихую деградацию, при которой пользователь получает резюме с двумя кнопками вместо пяти и никакой ошибки. Вторая ловит поломку кэширования — единственный отказ в этой схеме, который проявляется **только** счётом и больше ничем.

**Троттлинг Bedrock становится вероятнее.** Один запрос клиента — до шести обращений к модели, пять из них одновременных. При зарезервированной конкурентности 10 это до пятидесяти параллельных вызовов. Алярм на любой троттлинг был и раньше; теперь он не формальность, а первое, что сработает под нагрузкой.

### Расход считает функция, а не биллинг

AWS Budgets для этого не годится: данные о затратах отстают на часы, а к моменту срабатывания деньги уже потрачены.

Функция знает число токенов на входе и выходе и цену использованной модели. После каждого ответа она публикует в CloudWatch собственную метрику `EstimatedCostUsd`. Алярм — на суточную сумму. Задержка минуты, а не часы.

Регион один, поэтому и метрика одна, и алярм один.

Цены моделей — переменные окружения рядом с их идентификаторами: сменили модель, сменили и цену.

AWS Budgets остаётся, но как страховка на весь аккаунт, а не как механизм остановки.

Алярм заведён на SNS. Ручка для остановки уже есть — флаг доступности сервиса, шаг 0 конвейера.

## Конфигурация Lambda

| Параметр | Значение |
|---|---|
| Память | 128 МБ |
| Таймаут | 50 с |
| Рантайм | Go, `provided.al2023` |
| VPC | нет |
| Конкурентность | зарезервированная, потолок против расходов |

128 МБ — функция ждёт Bedrock, а не считает. Оплата идёт за гигабайт-секунды, и на многосекундном стриминге минимальная память экономит вдвое против 256. **Проверить на этапе каркаса:** при 128 МБ доля vCPU мала, и если перекладывание потока в SSE начнёт добавлять задержку — поднять до 256. Замер делается один раз, правка в одну строку.

Таймаут поднят с 30 до 50 с: теперь ответ — это фаза 1 плюс фаза 2 последовательно, и хотя вызовы фазы 2 идут параллельно, полное время выросло примерно вдвое. Прежние 30 с рассчитывались на один ответ модели.

**Почему 50, а не 60.** Таймаут чтения origin на CloudFront обязан быть строго выше таймаута функции: иначе на длинном ответе гонку выигрывает CloudFront, и пользователь получает обрыв вместо ответа. А у CloudFront свой потолок — 60 с, выше только через запрос на увеличение квоты. Отсюда единственная связка, которая работает из коробки: **функция 50 с, CloudFront 60 с.** Десять секунд запаса, никаких обращений в поддержку.

Бюджет сходится: фаза 1 до ~20 с, срок фазы 2 — 25 с, итого 45 с при потолке 50.

Клиентский таймаут держится выше серверного, иначе расширение сдастся раньше, чем функция ответит.

**Фаза 2 имеет собственный срок**, заметно меньше общего: вызов, не уложившийся в него, бросается и уточнение не приезжает. Иначе один зависший вызов из пяти держит весь ответ до таймаута функции, и пользователь не получает ни `done`, ни оставшихся четырёх уточнений.

Вне VPC намеренно: Bedrock и DynamoDB доступны через публичные эндпоинты, VPC добавила бы NAT Gateway и задержку холодного старта без выигрыша. Плюс Function URL не поддерживает стриминг внутри VPC.

Пороги, квота, оба потолка токенов, максимум кнопок, срок фазы 2, список языков, флаг доступности и текст `message` — переменные окружения, задаются в Terraform. В коде не зашиваются: их меняют без релиза расширения и без пересборки функции. Клиенту ни одно из этих значений не отдаётся.

Каталог кнопок собирается из `catalog.json` на сборке бэкенда: enum схемы и таблица `id → description` для промпта — из записей без `deprecated`, `instruction` для фазы 2 — из всех.

**Тест сборки:** `version` равна максимальному `since`; все `since <= version`; `id` уникальны; `description` и `instruction` непусты у каждой записи. Не проходит — сборка падает.

**Содержимое каталога — отдельная задача разработки бэкенда.** Схема зафиксирована, файл пока пуст. Придумывать кнопки заранее, в отрыве от промпта и от первых прогонов на реальных текстах, смысла нет: `description` — это критерий выбора для модели, и подбирается он по её поведению, а не умозрительно.

Работы, которые этот файл блокирует: enum схемы инструмента, таблица `id → description` в промпте, промпты фазы 2, файлы `_locales/<lang>/buttons.json` и тест подписей в расширении. Каркас всех пятерых пишется на пустом каталоге, наполнение приезжает одним заходом.

## Прогрев

Компиляция грамматики strict-схемы кэшируется на стороне Bedrock ограниченное время. Первый запрос после простоя может ловить дополнительную задержку.

Проверить на этапе 1. Если подтвердится — периодический прогревающий вызов по расписанию.
