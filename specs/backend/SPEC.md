# Бэкенд

Одна Lambda на Go в одном регионе (`us-east-1`), Function URL в режиме `RESPONSE_STREAM`. Роутинг по пути внутри функции.

## Эндпоинты

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/v1/summarize` | сжать текст, предложить кнопки |
| POST | `/v1/expand` | ответить на вопрос кнопки |
| GET | `/v1/config` | действующие лимиты и флаг доступности |

Health-эндпоинта нет. Балансировщика, который выводил бы нездоровые инстансы из ротации, в схеме не существует, а живость видна по метрикам реальных вызовов. Отдельный путь потребовал бы исключения в правиле `Origin` на WAF — дырка ради функции, которая ничего не даёт.

### `/v1/config`

```
minInput   int
maxInput   int
languages  []string
enabled    bool
message    string   // текст для пользователя, когда enabled = false
```

Значения читаются из переменных окружения функции. Квота и потолок токенов **не отдаются** — клиенту они не нужны, остаток запросов пользователю не показывается.

`enabled: false` — аварийный выключатель. Меняется через `terraform apply`, без релиза расширения.

### `/v1/summarize`

```
text   string
lang   string
ratio  light | normal | tight
source selection | page | manual
```

### `/v1/expand`

```
text     string
summary  string
actionId string
lang     string
```

Stateless: исходный текст приходит заново. Серверное хранение или кэширование пользовательских текстов запрещено.

Ответ обоих — SSE по протоколу из спеки архитектуры.

## Конвейер обработки

1. Валидация тела; `lang` по списку из конфига → `unsupported_language`.
2. Проверка длины по порогам из конфига → `too_short` / `too_long`. Эвристик «осмысленный ли текст» нет.
3. Квота в DynamoDB → `rate_limited`.
4. Вызов Bedrock `ConverseStream`.
5. Перекладывание потока в SSE.
6. `done`.

Шаги 1–3 выполняются **до** обращения к Bedrock. Ошибка на любом — SSE-ответ с единственным событием `error`, код 200 на уровне HTTP.

Проверки шагов 1–2 дублируют клиентские намеренно. **Сервер здесь единственная инстанция**: клиентская проверка — только экономия запроса, доверять ей нельзя.

**`Origin` функция не проверяет.** Это делает WAF на CloudFront: отклонённый запрос не доходит до Lambda, вызов не оплачивается. С учётом OAC запрос с чужим `Origin` до функции физически не доедет.

## Bedrock

`ConverseStream`, модель класса Haiku / Nova Lite, обращение через cross-region inference profile.

**`tool_choice: auto`.** Форсировать вызов инструмента запрещено: форсированный выбор подавляет текстовый блок, и резюме не будет.

### Инструмент

```
name: suggest_actions
strict: true
input schema:
  ids:     array, maxItems 5, items: enum <полный каталог>
  docType: enum <типы документов, включая other>
  srcLang: string
```

`docType` — тип текста по мнению модели: `news`, `article`, `product`, `scientific`, `legal`, `howto`, `thread`, `other`. Значение `other` обязательно: без запасного варианта закрытый перечень вынуждает модель отнести непонятный текст к ближайшей категории, и статистика начинает врать.

`docType` и `srcLang` идут **только в лог**. Клиенту не передаются, на подбор кнопок и на поведение не влияют. Нужны, чтобы группировать статистику по типу материала при настройке каталога.

`strict: true` даёт constrained decoding: ID вне enum физически не может быть сгенерирован.

Схема инструмента **статична и байт-идентична между запросами**. Динамическая сборка схемы (например, фильтрация enum под версию клиента) запрещена — плодит грамматики и дробит prompt-кэш.

### Порядок запроса

```
[системный промпт + каталог + описание инструмента]   ← статика
--- cache breakpoint ---
Output language: <lang>
Compression: <ratio>
<текст пользователя>                                   ← переменная часть
```

Переменная часть строго после точки кэширования. Нарушение порядка обнуляет prompt caching.

### Промпт

На английском. Локализация запрещена.

Обязательно содержит **явное указание, когда инструмент вызывать не надо**: текст слишком короткий, бессвязный, не содержит предмета для уточнения. Оставленный неявным, этот случай ведёт себя недетерминированно.

Исходный язык текста в промпте не указывается — модель определяет сама.

## Разбор ответа модели

Блоки обрабатываются **по типу, а не по порядку** — очерёдность текстового блока и вызова инструмента при `auto` не гарантирована.

| Тип блока | Действие |
|---|---|
| `text` | каждый чанк → событие `delta` |
| `toolUse` | накопить, разобрать; `ids` отфильтровать → событие `actions`; `docType` и `srcLang` → лог |

Инструмент не вызван → `actions` с пустым массивом. Подстановка дежурных ID запрещена.

### Фильтрация ID

Из полученного списка оставить те, что: есть в каталоге; имеют `since <= X-Catalog-Version`. Обрезать до пяти.

Первая проверка — страховка, enum её уже гарантирует. Вторая — обязательная логика совместимости версий, без неё старый клиент получит кнопку без подписи.

## Параметры запроса

Модель, потолок токенов и дневная квота не константы. Они разрешаются на каждый запрос по цепочке, первое найденное выигрывает:

```
1. переопределение для этого deviceId   (таблица overrides)
2. набор для географического тира        (env)
3. глобальный дефолт                     (env)
```

Разрешённый набор пишется в лог — иначе при разборе жалобы непонятно, какой моделью отвечали.

### Тиры

Тир определяется по стране. **IP-адреса собирать не нужно:** CloudFront сам определяет страну на краю и передаёт двухбуквенный код в заголовке `CloudFront-Viewer-Country`. Функция видит `US`, а не адрес.

Два набора: `tier1` и `rest`. Список стран тира 1 и параметры обоих наборов — переменные окружения.

VPN даёт страну выходного узла. Это принимается как есть и не лечится.

### Переопределения по устройству

Отдельная запись в DynamoDB, ключ `device#<deviceId>`, без TTL:

| Поле | |
|---|---|
| `model` | идентификатор модели, необязательно |
| `maxOutputTokens` | необязательно |
| `dailyQuota` | необязательно |
| `email` | необязательно |
| `note` | зачем заведено, для людей |

Незаполненные поля падают на следующий уровень цепочки.

**Записи создаются вручную.** API самообслуживания нет и не планируется: эндпоинт, позволяющий поднять себе лимиты, — это и есть дыра.

Чтение — один `GetItem` на запрос, рядом с проверкой квоты.

**`email` — персональные данные.** До того как поле начнёт заполняться, нужны политика приватности с упоминанием этого факта, декларация сбора данных в Chrome Web Store и способ удалить запись по запросу. Пустое поле этих обязательств не создаёт.

## Квоты

DynamoDB, одна таблица, два вида записей по префиксу ключа:

| Ключ | Что | TTL |
|---|---|---|
| `quota#<deviceId>#<YYYY-MM-DD>` | счётчик запросов за сутки | +48 часов |
| `device#<deviceId>` | переопределения | нет |

Инкремент — одной операцией `UpdateItem` с `ConditionExpression` на лимит. Чтение с последующей записью запрещено: параллельные запросы обойдут лимит.

`summarize` и `expand` считаются одинаково. Отказ → `rate_limited`.

Очистка не реализуется — TTL удаляет счётчики сам, переопределения живут до ручного удаления.

Регион один, поэтому `ConditionExpression` даёт настоящую гарантию: обойти лимит параллельными запросами нельзя.

## Логирование

CloudWatch, структурированный JSON, одна запись на запрос.

**Пишем:** длину входа, `source`, `lang`, `ratio`, `docType`, `srcLang`, выбранные ID, `emptyActions: boolean`, код страны, разрешённые модель и лимиты, латентность до первого токена, полную латентность, токены, оценку стоимости, код ошибки.

`emptyActions` алярма не имеет, но в логе остаётся: это единственный способ понять, для каких материалов каталог кнопок работает плохо.

**Не пишем ничего из текста пользователя** — ни исходник, ни резюме, ни фрагменты. Ошибки Bedrock логируются без эхо содержимого запроса.

Устойчиво высокая доля `emptyActions` на нормальном трафике означает, что промпт слишком строг. Смотрится вручную при настройке каталога, алярма не требует.

## Метрики и алармы

| Метрика | Алярм |
|---|---|
| **Расход за сутки** | **> $20** |
| Латентность до первого токена | p95 > 1.5 с |
| Доля `upstream_error` | > 2% за 15 мин |
| Троттлинг Bedrock | любой |
| Ноль успешных ответов | 3 часа подряд при обычном трафике |

Последний заменяет собой проверку живости: при живом трафике его отсутствие само по себе сигнал, и стоит это ноль.

### Расход считает функция, а не биллинг

AWS Budgets для этого не годится: данные о затратах отстают на часы, а к моменту срабатывания деньги уже потрачены.

Функция знает число токенов на входе и выходе и цену использованной модели. После каждого ответа она публикует в CloudWatch собственную метрику `EstimatedCostUsd`. Алярм — на суточную сумму. Задержка минуты, а не часы.

Регион один, поэтому и метрика одна, и алярм один.

Цены моделей — переменные окружения рядом с их идентификаторами: сменили модель, сменили и цену.

AWS Budgets остаётся, но как страховка на весь аккаунт, а не как механизм остановки.

Алярм заведён на SNS. Ручка для остановки уже есть — флаг `enabled` в конфиге.

## Конфигурация Lambda

| Параметр | Значение |
|---|---|
| Память | 128 МБ |
| Таймаут | 30 с |
| Рантайм | Go, `provided.al2023` |
| VPC | нет |
| Конкурентность | зарезервированная, потолок против расходов |

128 МБ — функция ждёт Bedrock, а не считает. Оплата идёт за гигабайт-секунды, и на многосекундном стриминге минимальная память экономит вдвое против 256. **Проверить на этапе каркаса:** при 128 МБ доля vCPU мала, и если перекладывание потока в SSE начнёт добавлять задержку — поднять до 256. Замер делается один раз, правка в одну строку.

Таймаут 30 с при типичном ответе в 5–15 с. Клиентский таймаут держится выше серверного, иначе расширение сдастся раньше, чем функция ответит.

Вне VPC намеренно: Bedrock и DynamoDB доступны через публичные эндпоинты, VPC добавила бы NAT Gateway и задержку холодного старта без выигрыша. Плюс Function URL не поддерживает стриминг внутри VPC.

Пороги, квота, потолок токенов, список языков и флаг доступности — переменные окружения, задаются в Terraform. В коде не зашиваются: их меняют без релиза расширения.

Каталог кнопок собирается из `catalog.json` на сборке бэкенда.

## Прогрев

Компиляция грамматики strict-схемы кэшируется на стороне Bedrock ограниченное время. Первый запрос после простоя может ловить дополнительную задержку.

Проверить на этапе 1. Если подтвердится — периодический прогревающий вызов по расписанию.
